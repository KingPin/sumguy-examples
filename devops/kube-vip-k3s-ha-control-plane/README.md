# kube-vip: a highly available k3s control plane

Companion files for [kube-vip: HA k3s Control Plane](https://sumguy.com/kube-vip-k3s-ha-control-plane/).

## What it does

kube-vip runs as a DaemonSet on the k3s server nodes. One server holds a virtual IP (VIP) for the Kubernetes API on port 6443. If that server dies, another one takes the VIP over through a Kubernetes lease (`plndr-cp-lock` in `kube-system`). Your kubeconfig and your agents point at the VIP, so losing one server no longer breaks `kubectl` or node registration.

- `k3s/server1-config.yaml`, `k3s/server-join-config.yaml`, `k3s/agent-config.yaml`: `/etc/rancher/k3s/config.yaml` for the first server, the other servers, and agents. The VIP is in `tls-san`.
- `rbac.yaml`: the kube-vip ServiceAccount, ClusterRole and binding, copied from https://kube-vip.io/manifests/rbac.yaml.
- `kube-vip.yaml`: a DaemonSet manifest generated by kube-vip v1.3.1 for VIP `192.168.1.50` on `eth0`, ARP mode, control plane only (no Service load balancing).
- `generate-manifest.sh`: regenerates `kube-vip.yaml` for your VIP and interface.
- `lab/`: a throwaway 3-server k3s cluster in Docker that kills the VIP holder and times the outage.
- `results/failover-runs.txt`: raw output from the lab runs quoted in the post.

## Prerequisites and tested versions

- 3 k3s server nodes on one layer 2 network (same switch or VLAN), plus a free IP outside your DHCP range for the VIP
- Tested with k3s v1.37.2+k3s1 and kube-vip v1.3.1 (November 2026)
- Docker (to run `generate-manifest.sh` and the lab), `curl`, `openssl`

## How to run

1. Pick the VIP and find the interface name on the servers (`ip -br addr`). Regenerate the manifest:

   ```bash
   VIP=192.168.1.50 INTERFACE=eth0 ./generate-manifest.sh > kube-vip.yaml
   ```

2. On the first server, before installing k3s:

   ```bash
   sudo mkdir -p /var/lib/rancher/k3s/server/manifests /etc/rancher/k3s
   sudo cp rbac.yaml /var/lib/rancher/k3s/server/manifests/kube-vip-rbac.yaml
   sudo cp kube-vip.yaml /var/lib/rancher/k3s/server/manifests/kube-vip.yaml
   sudo cp k3s/server1-config.yaml /etc/rancher/k3s/config.yaml   # edit the token first
   curl -sfL https://get.k3s.io | sh -s - server
   ```

3. On servers 2 and 3, copy `k3s/server-join-config.yaml` to `/etc/rancher/k3s/config.yaml` and run the same install command. On agents, copy `k3s/agent-config.yaml` and install with `curl -sfL https://get.k3s.io | sh -s - agent` (a bare `sh -` installs a server).

4. Check the VIP, then point your kubeconfig at it:

   ```bash
   kubectl -n kube-system get lease plndr-cp-lock -o jsonpath='{.spec.holderIdentity}{"\n"}'
   sed -i -E 's#https://(127\.0\.0\.1|192\.168\.1\.11):6443#https://192.168.1.50:6443#' ~/.kube/config
   ```

### Lab: time a failover on your laptop

```bash
cd lab
./failover-test.sh          # brings the cluster up, kills the VIP holder, cleans up
KEEP=1 ./failover-test.sh   # same, but leaves the containers running
```

The lab uses privileged containers on a Docker bridge network (`172.31.250.0/24`, VIP `172.31.250.100`). It is for testing only.

Results from eight failover runs on a single desktop (runs 1 and 3 to 9 in `results/failover-runs.txt`): the VIP stopped answering for 21.6, 16.2, 17.5, 17.5, 48.3, 25.9, 17.4 and 18.6 seconds after `docker kill` of the holder. Median 18.1 s. The 15 second lease duration sets the floor; the 48.3 s run was not traced. Run 2 failed during cluster start-up, before the failover step: `kv-server1` exited and the cause was not traced. `restart: on-failure` in `compose.yaml` was added after it; runs 4 onward used it. Run 6 came from a separate review session with the same script.

If the VIP gives an x509 error, add it to `tls-san` on every server, then `systemctl stop k3s`, `k3s certificate rotate`, `systemctl start k3s`.
